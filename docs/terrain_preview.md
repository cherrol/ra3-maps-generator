# 公共游戏地形预览流程

制作预览时，用户只需提供真实地形参考资料，并说：

> 以 xxx 为蓝图制作游戏地形图。

`xxx` 可以是地形原型或已定地图名。Codex 负责识别本次提供的资料、查阅 `docs/九州大地命名.md`、准备参数并完成预览，用户无需另外编写配方、指定算法或重复确认文件名。只有参考资料缺失或无法确定对应蓝图时，才补充必要信息。

## 输入与命名

真实地形图、已有高程数据和可选的边界、水域资料均在制作时提供，不把某张图的地理范围、数据下载地址或名称写成公共默认。海拔切点采用下文的全国基础标准，允许按当地真实地形调整并记录。优先使用当前提供的蓝图，原始文件保存在该地图 `data/` 内供回查。

地图名称与系列展示名查阅 [九州大地命名](九州大地命名.md)。真实地形名用于本地目录和 CLI id，预览标题继续用“九州大地·地图名”。例如，输入“云南”或“层峦织彩”均保存到 `maps/云南/`，标题仍为“九州大地·层峦织彩”，不新建生成名目录。

- **提供高程资料**：使用公共 Rust 入口确定性地生成预览；有水域、主体轮廓和经纬度信息时一并读取。
- **只提供参考图片**：读取图片中的山岭、谷地、平原、水域和方向，以原图为视觉蓝图制作设计分层。使用图像生成或编辑能力时按 `imagegen` 技能处理原图，并保持三图同一取景。图中没有的测量高程不作为已知数据；无需要求用户另外寻找 DEM 或填写 JSON。

## 统一步骤

1. **识别蓝图并定名**：读取本次参考资料，按 docs 确定地图目录和展示名称。
2. **确定中心与游戏范围**：以蓝图主体为中心确定完整地理取景，可玩网格固定为 **800×800 格正方形**。保留现有地理取景，两个坐标轴分别重采样到 800 格；不按原取景比例保留矩形网格，也不裁掉主体。制作网格四周另留 20 格边框，因此含边框为 **840×840 格**。此处尺寸是地形格数，不是带图例 PNG 的像素尺寸。画面北朝上，保留主体完整轮廓。
3. **补齐整个游戏矩形**：主体边界是地理参考线；边界外、游戏矩形内的真实地形也属于游戏地形。仅裁掉游戏矩形以外的部分，不沿省界挖空、留黑或改成背景地形。
4. **整图统一分层**：整个矩形采用相同海拔／地貌判读、平滑、切层、层界整理、碎块合并和窄颈整理。省界不参与切层或区域合并。水域以蓝图为依据，按下文游戏水域整理规则处理细长条、分叉与碎水。
5. **映射设计高度**：采用全国基础海拔切点 200、500、1500、4000 米，映射游戏高度 210、280、350、420、700；第五层可按图采用 500–1000 的高山设计高度。各图保留 2–5 个实际存在的陆地层级，水域单独计算。局部调整遵守下文三条规则。第五层的禁行设计在预览中标明，实际通行留待之后制作地图落实。
6. **分别绘制原图与处理结果**：原始图保持真实地形信息；处理图只呈现统一的游戏分层；边界版使用完全相同的分层，额外画地理参考线和矩形游戏外框。边界不改变地形。
7. **核对并保存**：三图朝向、取景、画幅和水域位置一致，主体完整入镜，矩形内没有缺失地形；检查层高与分层对应，以及提供的原始资料得到保留。

## 全国基础分层与局部调整

| 层级 | 真实海拔基础区间（含下限、不含上限） | 默认游戏设计高度 |
|---|---|---|
| 第一层 | 低于 200 米的陆地 | 210 |
| 第二层 | 200–500 米 | 280 |
| 第三层 | 500–1500 米 | 350 |
| 第四层 | 1500–4000 米 | 420 |
| 第五层 | 4000 米及以上 | 700，禁行高山设计 |
| 水域 | 以真实水域为依据的当前设计掩码，与陆地海拔分段分开 | 预览水底 130 |

以下三条适用于整个游戏矩形，省界不参与判定：

1. **不强求五层**：没有的高度层直接省略；整理后的小碎层并入相邻层。图例只显示实际保留的层及对应真实海拔区间，保留全国层号与对应游戏高度，不为凑数造山。
2. **不足两层时局部补分**：纯平原或高原地图可能全部落在一个区间，应按当地真实高程进一步划分，并记录调整后的阈值。公共实现依次尝试平滑陆地高程的 50%、40%、60%、30%、70% 分位点；优先选择经相同连片、碎块和窄颈整理后能保留两层的切点，映射为游戏高度 210、280。完全平坦或过于破碎、无法按真实高程补分的资料应明确报错，不虚构地形。
3. **高原不能整片禁行**：青海、西藏等地图应提高高山层门槛，让宽阔高原面保留为可玩台地，第五层禁行区主要留给突出山脊和山峰。公共实现以平滑后陆地海拔中位数达到 3000 米识别高原主体，将第五层门槛提高到原切点、90% 分位高程和中位高程加 750 米三者的最大值；第五层没有保留区域时直接省略，仍不足两层则按第二条补分。这是预览设计标准，不是地理学分区或实际游戏通行验收。

真实海拔先平滑再切层，并继续做连片整理，因此最终各格未处理的真实海拔可能跨越名义区间。原始真实高程保留不变。每张图的 `data/terrain-preview/report.json` 记录全国基础切点、请求切点、最终切点、调整原因、实际层号和各层面积。

## 水域显示

2026-10-28 用户要求现有六图去掉河流，仅保留海洋及面积较大的湖泊、水库。本轮以真实多边形轮廓估算的 **80 平方公里**为湖泊、水库保留门槛；这是可调整的游戏设计筛选值。面积按完整水体、扣除岛屿后计算，再裁到游戏矩形，不按裁后面积淘汰跨边界的大湖。来源筛选与游戏岸线设计分别记录；局部填合遵守下文规则，不以凑海战面积为由任意扩大湖泊。

- 海洋使用真实海洋多边形，避免把河道、低于海平面的陆地或高程异常点误判为海；本轮再用半径 3 格的开运算清理伸入内陆的细窄水道，保留开阔海域。
- 河流中心线与河道水面不加入预览；海洋数据中的海湾、宽阔河口按海域保留。
- 将满足面积门槛的湖泊、水库多边形与海洋掩码合并为来源水域，再进行游戏水域整理，不再叠加河流线；当前设计结果写入 `water_mask`，来源掩码另行保留。
- 三张基础图及已有中心标点图采用同一当前设计水域掩码；`source.png` 的真实高程不变，其水域着色也使用该掩码。筛选前与整理前的参考 NPZ、水域和河流资料保留在内部原始输入中供回查。
- `parameters.json` 的 `water_policy` 和生成报告记录筛选规则；`water-policy.json` / `water-report.json` 保存各水体的估算面积、取舍及格数。面积来源是参考矢量的估算值，不称为实测或法定面积。

### 游戏水域整理

游戏地形预览默认避免细长条、窄颈分叉和零散碎水。相邻水体或同一水库的支汊，能够局部填合的优先合并并圆整为宽阔、闭合的连片水面；无法合理合并的细小水域并入附近实际相邻的陆地层，并整理局部层界。按当地地形就近处理，不跨越大片陆地串连远处湖泊，也不要求全图水域合成一块或画成环形。

水陆两侧对称检查：伸入水域的细长陆地、窄颈半岛和尖细尾部同样需要整理。优先就近收拢、圆整或拓宽成宽阔主体；无法合理保留的细条并入周围水域。按最终游戏框检查，保留真实高程与来源轮廓，记录设计岸线的变化。

小岛和小水域采用**整圈边界连续、可双向跨层通行**的设计，所有边界位置都能通向相邻层级；只留少数坡口、单一出口或仅验证中心可达，均不满足该要求。纯预览在本图参数或过渡设计记录中声明完整岸线的连续过渡范围；推进可玩制作时，沿全周落实连续缓坡或相应水陆过渡，逐段核对宽度、坡度、阻挡和导航。预览色块接触及二维连片检查只说明设计关系，不替代实际游戏通行验收。

- 修改前保留完整原始输入和来源水域掩码；真实高程、地理边界、取景和北向保持一致。设计岸线与来源轮廓分别记录，整理后不再声称当前水域严格等于原始湖海轮廓，也不把新增水面格数称为真实面积。
- 合并、填凹和圆整方法按本图选择；宽度、面积和处理半径按本图尺度确定，不把单图的水体数量、坐标或数值阈值写成公共要求。数值预览先整理输入 `water_mask`，再用原生 `terrain-preview` 生成；当前 `water_policy` 仅记录规则，单独填写不会执行整形。
- 仅修改已有预览水域时，保存整理前的 `terrain.npz` 和 `report.json`，在本图参数中配置 `water_design_land_reference` 的 `terrain`、`report` 相对路径（以 `data/terrain-preview/` 为基准）。原生生成沿用原有陆地层级和最终海拔切点，只将移除的水域就近接入相邻陆地层；核对仍为陆地的原格层级不变，避免水域变化触发整图分位切层或碎层传播。
- 规则与结果保存到本图 `data/terrain-preview/`，同步更新参数、水域统计和核对记录。基础三图及已有中心标点图均从同一设计掩码重绘，保持地形数组与图片一致。
- 核对残留碎水、细长分叉与窄颈，确认保留水面宽阔连片、移除水域已接入有效相邻陆地层，局部层界衔接正常，原始资料和同取景条件得到保留。明确要求原样展示真实岸线时遵从当次要求。

## 最终图片

地图目录根部保留以下三张基础预览，以及配置了行政中心数据时的中心标点图，不产生 `v1`、`v2` 等中间图片：

| 文件 | 内容 |
|---|---|
| `source.png` | 与最终游戏范围同取景的真实地形参考图，未做游戏分层 |
| `preview.png` | 整个游戏矩形统一处理的分层地形，无边界标注 |
| `preview--line.png` | 同一张分层地形，加主体地理参考线和游戏地图外框 |
| `preview--center--line.png` | 同一张带边界的分层地形，叠加行政中心标点、名称和必要的引线 |

输入、内部参数、分层数组和核对记录放在 `data/terrain-preview/`，不作为额外最终图片交付。纯地形预览不加入出生点、矿、建筑、队伍或脚本，不递增地图版本、不打包安装；预览完成即交付三图。

Git 同时跟踪这些图片、当前 NPZ 输入与分层、参数、来源和核对资料，以及参数/报告引用的设计快照；下载瓦片与日志继续忽略。离线复现命令和实际可玩图图片的版本归档见[可复现构建](reproducible_builds.md#预览与实际游戏地图)。

## 高程资料的公共执行入口

Codex 根据当次资料执行，例如：

```sh
cargo run --release --locked -- terrain-preview <蓝图原型或已定地图名> <提供的高程NPZ>
```

命令在完整地图配方建立前即可使用，不依赖 `config.json`、`layout.json`、八个出生点或版本文件。命名从 docs 动态读取，不修改 `maps/.default`。优先读取 `maps/<真实地形名>/data/terrain-preview/parameters.json`，兼容已有的根目录 `preview.json`；没有配置时采用全国基础切点并执行上述三条规则。预览重做不改动可玩地图的配方、定稿分层数组或制作源。`map_id` 记录真实地形名，`map_name` 保留生成展示名；设计坐标声明中的缓存路径相对工程根目录。

NPZ 按第 0 行为北排列，包含：

| 数组 | 含义 |
|---|---|
| `elevation_m` | 必需，二维真实高程 |
| `water_mask` | 可选，同尺寸 0/1 当前设计水域掩码；来源与整理规则分别留档，缺省按高程不高于 0 判定水域 |
| `land_mask` 或 `inside_province` | 可选，蓝图主体的 0/1 轮廓，用于取景和参考线，不裁切游戏地形 |
| `bounds_wgs84` | 可选，完整输入网格的 `[西, 南, 东, 北]` 经纬度范围 |

命令自动选择贴近主体的地理范围，保持完整地理取景，将宽高分别重采样为固定 **800×800 格**正方形。高程双线性采样，边界与水域用最近邻采样，整图统一生成游戏分层。报告的 `game_cells` 为不含边框的可玩范围，`size_policy` 记录正方形要求、800×800 格尺寸、独立轴重采样及来源尺寸，制作网格另加四周各 20 格边框。原始参考拷贝、地形数组、参数、图像校验和及范围记录保存在 `data/terrain-preview/`。原有成品构建的 `preview` 阶段继续用于布局预览，与这里的制作前纯地形流程分别使用。

## 行政中心标点

2026-10-29 用户要求为 `maps/` 的全系列预览添加行政中心标点，并单独输出 `preview--center--line.png`。省、自治区标地级市及自治州、盟、地区中心；四个直辖市标各区中心，不把县当作区。港澳按分区中心，台湾按县市中心。省直辖的县级市、县等不冒充地级行政区；数据源把它们标为 city 时仍按六位行政代码过滤。

各图的 `data/terrain-preview/centers.json` 保存 `map_name`、`label`、`coordinate_system: "WGS84"`、`source` 和 `points`；每个点包含 `adcode`、`name`、`center_wgs84: [经度, 纬度]`。采用行政中心坐标，不采用行政区域多边形的几何质心。下载原始响应保存在同目录 `raw/`，保留来源、坐标转换和数据补充记录。GCJ-02 来源先转为 WGS84，与预览地形使用的地理坐标一致。

仅追加标点图时使用原生离线命令：

```sh
cargo run --release --locked -- terrain-preview-centers <蓝图原型或图名>
```

命令读取现有 `terrain.npz` 分层和 `report.json` 的实际游戏经纬度范围，保持相同画幅、北向、地形、水域与边界，保留三张基础图、地形缓存和可玩地图配方的原始字节。无需重做高程分层、修改版本或安装游戏地图。中心点固定在实际投影位置；名称避让其他名称及标点，必要时用引线连接。游戏取景之外的中心不移到画面边缘，也不扩大地图；在 `centers-report.json` 的 `outside_frame` 中列明。报告同时记录图中坐标、名称框、点数及图片校验和。

以后重新运行 `terrain-preview` 时，如存在有效的 `centers.json`，会同时生成第四张中心标点图；没有中心数据时仍生成原来的三张基础图。
