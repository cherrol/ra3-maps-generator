# 地形封装流水修复与地编保存对照

用户确认：代码发布的千壑横原 T0.7.3 岩壁有黑块，经地编保存后游戏内正常。本次先冻结游戏目录中的已保存成品，再与 dist 原包逐文件、逐区块、逐格比较。未覆盖游戏目录中的这份已验证地图。

| 山体高度 | 一致 | 一致 |

| 原生 `WorldInfo.terrainTextureStrings` | 仍为旧 9 项材质；缺少新岩石 | 按实际材质重新生成，包含新棕岩 |

地编保存还清理了未使用字符串，将 456 个对象的 `uniqueID` 重新编号，把 6 个矿的角度从 −π 归一化为 +π，并调整脚本排列。544 个对象的位置与类型未变，352 条脚本逐条内容一致。为保护对象身份，流水修复采用原 dist 包，未整体替换为地编保存后的二进制。

## 漏项所在

1. `ramps/peaks/rework.rs` 添加新材质时更新了 `BlendTileData`，增量发布只扩充 XML `Tile`，遗漏原生 `WorldInfo` 和 XML `WorldDict` 中的加载清单。历史回读显示 T0.7.0 首次加入 `Rock_Yucatan03` 后即出现该不一致，直到 T0.7.3 一直存在。
2. `ramps::patch_blend` 每次编辑都从空缓存开始追加混合描述，既有描述未复用；发布阶段也未清除未引用项。混合表从 T0.6.0 的 3,243 条积累至 T0.7.3 的 8,500 条。
3. `release::retarget_xml` 原本只改文件路径并刻意保留旧资产 ID，缺少针对地图和图集的版本刷新。
4. 旧发布校验只检查图集数量、材质 ID 和配套文件存在，没有交叉核对三份材质声明，因而放过“图集中有新岩石、加载清单却没有”的成品。

加载清单不完整是确定的封装缺陷，与新增岩石显示异常直接相关。地编保存同时更改清单、资产 ID 和混合表，尚未单独通过游戏 A/B 实测拆分三者的视觉贡献；本报告不假定未经证实的混合记录硬上限。此前仅排序的 T0.7.3 修正不完整。

## 公共流水中的具体故障环节

这次实际触发的入口是 `add-mountains`，它从 `main.rs` 直接调用 `release::run_inner`，没有经过新蓝图的 `build::assemble`。因此不能把新蓝图组装中已有的 `WorldInfo` 生成逻辑，当成增量编辑也会执行的步骤。

| 环节 | 旧代码行为与责任 |
|---|---|
| 山体写入：`ramps/peaks/rework.rs::append_materials` | 只给 `BlendTileData` 增加岩石家族，加载清单在此开始与材质表分离。这是底层局部编辑，需要发布层完成配套同步。 |
| 增量成品组装：`release::run_inner` 的 `Edit::Mountains` 分支 | 调用山体编辑后，只执行 `extend_terrain_atlas`，随后直接编码 `.map`；遗漏同步 `WorldInfo`、XML `WorldDict`。**这是本次直接产生不完整成品的责任环节。** |
| 公共 `map` 阶段：`coordinate_pipeline::assemble` | 千壑横原启用了 `COORDINATE_PIPELINE`，公共 `build` 会走该分支。旧逻辑复制冻结成品，主要响应对象坐标变化，没有补齐来源中的加载声明；因此再次构建延续了已有问题。 |
| `verify / accept / dist / install` | 旧的 `validate_files` 检查文件配套与图集成员，缺少“材质表 ↔ 原生加载清单 ↔ XML 加载清单”交叉检查，未阻止不完整成品发布。 |
| ZIP 与安装复制 | assets、dist、ZIP 内的 T0.7.3 `.map` 及检查前冻结副本 SHA256 全部相同；该步骤没有改坏地形数据。 |

普通新蓝图路径还有同类时序隐患：`build::assemble` 先生成 `WorldInfo` 和 XML，再运行纹理整理。原来的纹理整理使用已有材质，不代表它已造成这次新岩石缺项；但编辑结束后统一同步的职责也必须在这一分支补齐。当前最终同步已放在最后一次纹理修改之后、保存 `.map` 之前。

现有回归 `terrain_package_repairs_new_rock_preloads_and_publication_rejects_partial_sync` 构造完整图集但缺少两份新岩石加载声明的包，证明旧 `validate_files` 会通过、新发布检查会拒绝，随后完整修复入口能够补齐。阶段核对证据见 `work/mountain-save-diff/pipeline-stage-audit.json`，专项日志为 `stage-audit-regression.log`。

## 流水修复

`resources::sync_terrain_package` 在最后一次材质编辑后同步原生加载清单、XML 加载清单和图集，保留贴图文件名并刷新地图/图集版本 ID；对象、脚本和原生 `AssetList` 的身份保持。普通构建、地形/纹理增量编辑和坐标新版本共用该处理。

`terrain_package::compact` 删除未引用或重复的混合记录，同时重写普通混合、第二混合平面与悬崖 UV 的引用。完整保留混合方向、标志、双侧参数、子贴图相位，以及全部通行/建造/禁飞位图。材质家族总数不超过 **49** 时保留编号；超过时，从表尾开始删除超额的未使用家族，并重映射所有材质引用。使用情况包含主贴图、两套混合及悬崖 UV，不能只检查主贴图。同步过程移除 XML 图集中的对应旧项，更新两份加载清单；超过 49 种实际使用材质时拒绝发布，不自动改变绘制效果。`patch_blend` 直接复用已有的相同描述，阻止反复编辑持续追加。

2026-10-29 河南 T0.0.3 在 WorldBuilder 中报告 `Maximum number of textures exceeded (50). Limit is 49`。此前代码采用图集存储容量 64 作为检查边界，未覆盖地编实际加载上限；现在运行时发布、打包和安装检查均拒绝超过 49 项的材质表，历史源仍允许导入完整修复入口。

发布、ZIP 打包、安装及坐标成品验收通过 `validate_runtime_files` 检查材质引用、两份加载清单、图集和当前版本 ID。失败发生在写入 dist 或安装之前。历史包仍可导入修复；含旧资产 ID 的包需先迁移为新版本。明确选择旧纹理与旧坡形的历史复现保留原混合表字节，仍检查加载清单及发布元数据。

```sh
cargo run --release --locked -- repair-terrain-package --map <id> --bump \
  --note '同步地形加载声明并整理混合记录' '<完整源ZIP>'
```

旧的 `repair-terrain-atlas` 只适用于原生加载清单已正确的包；如果需要改动原生清单，它会拒绝并提示使用完整修复入口。

## 公共入口收敛与失败保护

后续优化将各分支分散的“整理混合表 → 同步清单 → 刷新 ID → 校验”收敛到 `resources::finalize_terrain_package`。该函数在暂存地图中处理，全部地形封装检查通过后才替换调用者的地图；异常 XML 或无效引用不会留下半更新的原生数据。普通构建先完成纹理修改，再生成资源包，移除了早期按旧材质单独写清单的重复逻辑；山体发布也移除了单独扩展图集的前置步骤。

冻结成品的 `map` 阶段现在在写入游戏文件前执行完整运行时校验，`adopt-coordinate-source` 在更新制作源、基准和配方前也执行同一校验。由此补上仅运行 map 或采用来源时绕过后续发布检查的缺口。旧包仍可作为显式修复输入导入。

校验路径复用一次解包后的地图，同时直接检查材质/混合/悬崖引用；不再为只读检查克隆整图、执行完整混合表整理和重新编码。完整整理只用于真正编辑地形的分支。

新增回归覆盖公共收尾失败不修改地图、成功操作可重复、仅 map 阶段拒绝残缺冻结包且不写文件，以及采用失败不改来源包、空间基准和配方。独立成品验证在 `work/common-terrain-finalization/` 中进行，使用冻结来源快照，不操作游戏进程。

本轮公共入口收敛后，102 项回归全部通过，相关模块定向 Clippy 通过。以冻结 T0.7.5 的独立副本执行全部构建阶段及 WorldBuilder 导出，六个成品文件与冻结来源、assets、dist、ZIP 逐字节一致。该工具链整理不改变现有成品字节，无需递增地图版本；记录见 `work/common-terrain-finalization/verification.json`。
