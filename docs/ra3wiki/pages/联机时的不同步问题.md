## 1. 不同步问题概述
联机不同步问题一直是地图开发中的难点。虽然日冕客户端提供了不同步报告生成功能，但在运行时会记录地图内所有物体的状态，造成较大的性能压力。如果参与联机的电脑配置较低，可能会引发严重的卡顿。此外，在一些复杂脚本中，不同步问题常常是概率性出现，即使使用不同步报告，也难以复现并定位问题。  



不同步的本质是由于不同的 CPU 执行相同逻辑但得出不同结果。例如，在联机时，如果有人启动外挂，修改了数据（如让某个目标无敌），会导致：

+ 电脑 A 计算该目标被击毁
+ 电脑 B 由于无敌效果，计算目标未被击毁

这种差异会导致不同步，并使游戏立即结束。



### 不同步问题的来源
a. **外挂和旧版日冕客户端**：如前述所述，当有人开挂时，可能会导致不同步。当有人使用旧版日冕客户端和新版联机时，即使游戏版本相同，在部分地图会由于客户端dll文件差异导致不同步。

b. **引擎 Bug**：在日冕 mod 开发过程中，仅发现了一个因引擎 bug 引发的不同步问题。该问题通过不同步报告文件初步定位，随后使用额外手段进一步追踪，最终得以解决。问题的根源在于 RA3 的一个模块在特定情况下使用了渲染坐标而非逻辑坐标，而渲染坐标在不同客户端之间存在差异，因而导致不同步。

c. **地图代码和设置**：这是本文关注的主要问题来源。随着对不同步现象的深入挖掘和理解，地图层面的问题或许有望追溯到引擎层面，从而帮助所有玩家和地图作者改进同步性能。

## 2. Lua 中的不同步问题
在 Lua 中，不同步问题主要源于以下几个原因：

### 随机数生成器的差异
Lua 自带的随机数生成器会导致不同步，因为不同的 CPU 可能使用不同的种子（seed）值来初始化随机数生成器。这会导致在不同计算机上生成的随机数不一致，从而产生不同的计算结果。为避免此问题，建议使用日冕 Lua 提供的 `GetRandomNumber()` 函数，该函数保证了所有玩家间随机数生成的一致性。

### 未定义的遍历顺序
> [https://www.lua.org/manual/4.0/manual.html#control](https://www.lua.org/manual/4.0/manual.html#control)
>

#### 使用了错误的循环语句
在遍历数组时，请勿使用 `for index, value in exp do block end` 格式的表格循环语句，因为该语句的遍历顺序未定义，不适合保证顺序的数组遍历。

正确的做法是使用数值 `for` 循环，格式为 `for var = e1, e2, e3 do block end`。例如：

```lua
local matchedObjects, count = ObjectFindObjects(nil, nil, nil)  -- 该函数返回一个包含地图上所有物体的数组
for i=1, count, 1 do
  local object = matchedObjects[i]
  -- 在此对 object 进行操作
end
```

> + <font style="color:rgb(0, 0, 0);">The order that table elements are traversed is undefined, </font>_<font style="color:rgb(0, 0, 0);">even for numerical indices</font>_<font style="color:rgb(0, 0, 0);">. If you want to traverse indices in numerical order, use a numerical </font>**<font style="color:rgb(0, 0, 0);">for</font>**<font style="color:rgb(0, 0, 0);">. --- 来自lua4.0手册中的原文</font>
>

#### 未索引数组的遍历顺序（高概率猜想）
未索引的数组在不同 CPU 上可能导致不同步问题，因为 **未索引数组的遍历顺序在不同的 CPU 或操作系统实现中可能有所不同**。

以下 `offsets` 数组示例看似简洁，但由于在 RA3 中使用的Lua 版本 4.0 在处理未索引数组时没有严格规定遍历顺序，因此每个 CPU 在读取数组时的顺序可能会不同，从而产生不同的结果。此情况在联机同步时可能引发不一致。

##### 错误的未索引数组例子：
```lua
local offsets = {
  {
    { x = radius, y = 0 },                          -- 0 degrees
    { x = -radius * 0.5, y = radius * 0.866 },      -- 120 degrees
    { x = -radius * 0.5, y = -radius * 0.866 },     -- 240 degrees
    { x = 0, y = 0 }                                -- center
  },
  {
    { x = radius * 0.866, y = radius * 0.5 },       -- 30 degrees
    { x = -radius * 0.866, y = radius * 0.5 },      -- 150 degrees
    { x = 0, y = -radius },                         -- 270 degrees
    { x = 0, y = 0 }                                -- center
  },
  {
    { x = radius * 0.5, y = radius * 0.866 },       -- 60 degrees
    { x = -radius, y = 0 },                         -- 180 degrees
    { x = radius * 0.5, y = -radius * 0.866 },      -- 300 degrees
    { x = 0, y = 0 }                                -- center
  },
  {
    { x = 0, y = radius },                          -- 90 degrees
    { x = -radius * 0.866, y = -radius * 0.5 },     -- 210 degrees
    { x = radius * 0.866, y = -radius * 0.5 },      -- 330 degrees
    { x = 0, y = 0 }                                -- center
  }
}
```

 通过为数组元素添加明确的索引（如 `[1]`, `[2]`），可以确保在任何环境下都按照相同顺序遍历，避免不确定性导致的不同步问题。  

##### 正确的完整添加索引的数组例子：
```lua
  local offsets = {
    [1] = {
      [1] = { x = radius, y = 0 },                            -- 0 degrees
      [2] = { x = -radius * 0.5, y = radius * 0.866 },        -- 120 degrees
      [3] = { x = -radius * 0.5, y = -radius * 0.866 },       -- 240 degrees
      [4] = { x = 0, y = 0 }                                  -- center
    },
    [2] = {
      [1] = { x = radius * 0.866, y = radius * 0.5 },         -- 30 degrees
      [2] = { x = -radius * 0.866, y = radius * 0.5 },        -- 150 degrees
      [3] = { x = 0, y = -radius },                           -- 270 degrees
      [4] = { x = 0, y = 0 }                                  -- center
    },
    [3] = {
      [1] = { x = radius * 0.5, y = radius * 0.866 },         -- 60 degrees
      [2] = { x = -radius, y = 0 },                           -- 180 degrees
      [3] = { x = radius * 0.5, y = -radius * 0.866 },        -- 300 degrees
      [4] = { x = 0, y = 0 }                                  -- center
    },
    [4] = {
      [1] = { x = 0, y = radius },                            -- 90 degrees
      [2] = { x = -radius * 0.866, y = -radius * 0.5 },       -- 210 degrees
      [3] = { x = radius * 0.866, y = -radius * 0.5 },        -- 330 degrees
      [4] = { x = 0, y = 0 }                                  -- center
    }
  }
```

注：   Lua 中的“数组”实际上是表。它们不具有数组的底层实现（例如连续内存分配），但可以用整数键模仿数组的行为。这种灵活性使得 Lua 表既可以用作数组，又可以用作字典，但也带来了与传统数组不同的行为。  

### 浮点数误差猜想
上述的offsets array中还有一个潜在问题，即使用了浮点数。

在不同的cpu中，浮点数的存储和计算可能有细微的误差，10^-7-10^-16量级。

浮点数误差是否需要在LUA层面考虑以避免不同步，在目前仍是一个尚未证实的猜想。

但是为了保险起见，推荐尽可能的使用整数运算来避免潜在的不同步风险。

下面是我们已知的信息：

> -- 信息来源：岚依公主
>
> -- lua 的问题在于他调用的一些数学函数，例如三角函数不是 lua 自己写的，也不是写死的汇编，而是调用微软 VC++ 库的函数
>
> -- lua里的所有数学函数，包括三角函数，甚至 ceil 和 floor，都是 VC++ 库提供的
>
> -- 因为无法保证每个玩家电脑上装的 VC++ 库的版本是一致的，所以计算结果会有细微的差别
>
> -- 部分开发者在MOD源码中不敢使用三角函数，因为浮点数的 IEEE 标准只规定了四则运算和 sqrt，对于其他的数学函数都没有特别的规定
>
> -- 但实际上地图群里的人测试过包括三角函数在内的各种数学函数，暂时尚未发现不同步
>
> -- (当然这也可能是因为测试人员的系统版本和 VC++ 库都是最新的，或者CPU 都是一样的)
>



注：**浮点数误差能够造成不同步是已被证明的事实。**

RA3和战网都是 **x86** 程序，但是ARM CPU的Windows用户(如Surface Pro X)仍然能上战网联机，但是一联机就会在游戏开始后几秒内不同步。

原因是ARM CPU的windows系统在运行RA3和战网时会自动把 x86 指令集翻译成 ARM 指令集，但是在联机时ARM玩家的计算结果仍然和大部分玩家的x86 cpu的浮点数计算结果不同。这里的不同步原因是在RA3引擎层面的计算差异造成的，根源是由于ARM CPU和X86 CPU属于不同的CPU架构（ISA指令集），在进行相同的运算时会出现不同结果。











## 3. 地编中的不同步问题
### 1. 有一定可能但未证实的不同步问题
下面是一些有可能造成不同步的点，因为难以100%证实或复现，只在这里列出为大家参考：

#### a. 单位跑出地图边界太远
这个例子来自卫国战争的作者报告，在地图外增加方形击杀框后，能够把不同步概率从50%降低至10%。

类似的结果来自诺曼底的版本测试，在将地图外的boss出生点移至地图内后，不同步概率大幅降低。

目前的猜测是，如果有单位或建筑长时间在地图外存在，那么就会存在基础的不同步概率（根据战网数据统计，概率约为10%）。存在某些lua代码，在运行时，会将这个不同步概率大幅提高至50%，而如果地图外没有单位/建筑，lua代码则不会放大不同步概率。

#### b. 地编队伍面板的随机数
这个例子来自最后机会日冕版的作者，为通过不同步报告定位。

如图所示，队伍面板里，可以指定每个单位类型的生成数量，有最大值和最小值。如果最小值小于最大值，那么每次生成的单位数量就会是随机的。而随机数，在不同的cpu上可能会产生不同的结果，导致cpuA生成了3个单位而cpuB生成了4个单位这种情况，导致不同步。
